# 0.2.21-buick.1 连接性能专项

更新：2026-10-25。用户明确：本版最高优先级是首次连接、后续连接和异常恢复的速度与成功率；秒级及亚秒级优化都要审查。本文是调查结果与实施顺序，不表示候选项已经修复。

## 测量边界

- 车机：FF-5000 / AC8227L，实际 Android 8.1 API 27，32 位 ARM，约 1 GB RAM。手机：iPhone 11 / iOS 18.7.7。
- 现场版本：code44，0.2.21-buick.1-debug。保留现有基线，本次不因性能调查切换上游版本。
- 当前计时起点是 controller start，不是车辆上电或点击图标。必须补充上电/唤醒、进程启动、点击连接的不同起点，避免把准备工作挪到计时前冒充优化。
- 以下时间来自车机同一时钟的日志；细分里程碑有 atNs，后续对比应使用单调时钟。日志落盘时间可能受队列影响。
- 无持续无线 ADB 读取的两次启动为 11.813 秒和 10.247 秒，均一次成功。这不是“首次清空配对”对照实验，也不是 P95。
- 有无线调试流量时发生过无用户操作的断开，重试耗时 35.468 秒。调试干扰有现场证据，但断开根因尚未确认。

| 阶段 | 安静样本 A | 安静样本 B | 意义 |
|---|---:|---:|---|
| controller start → 首个 TCP | 2.653 s | 2.503 s | 热点准备、服务、蓝牙、iAP2、手机网络接入 |

## 断开车机后的离线进展

进一步对齐 code44 原始日志：08:53:17.724 收到 /info，17.859 已生成响应，17.868 已记录 wireHex，19.638 才记录 response-buffered。约 1.77 秒集中在后半段。热样本对应后半段约 76 ms。由于这些时间是日志时间，不能据此直接证明是密码运算或网络阻塞；但优先级应从盲目缓存图标转为拆分加密与 socket 写入。

已在工作树补充控制响应计时，尚未装车验证：

- `handleMs`：从处理该请求开始到 handler 返回，包含前置请求诊断和回调。
- `encodeTraceMs`：handler 返回后，响应日志、RTSP 编码及完整 wireHex trace 的时间。
- `encryptMs`：控制响应加密时间；未启用加密时只是直通时间。
- `writeMs`：写入 BufferedOutputStream 的时间；大响应可直接写底层 socket，因此可能包含网络背压。
- `authFlushMs`：成功 POST /auth-setup 的提前 flush，单独测量且不包含后续认证回调。
- `responses-flushed`：解析批次最后一条 CSeq、条数、最终 flushMs 与单调 atNs。它只证明本地 flush 返回，不证明手机收到；仅 feedback/command 的批次不新增此条日志。

`processingMs` 保留原含义，含诊断及认证回调等开销，不要求等于各字段相加。最终 flush 的时间先采样，再执行原有 setup 通知，最后写新增 trace，避免新日志延迟 setup 通知。

重连路径已确认对 IPv4/IPv6 的多个 JmDNS 实例逐个 close，与约 4 秒的 Bonjour 清理一致。code45 已实现并行关闭并通过离线测试，资源跨会话复用仍未实现，需另行验证所有权。配对代码确有持久化保存与加载，没有发现“每次启动必定生成新身份”的直接逻辑，重复 pair-setup 仍不能判为已确认缺陷。

code45 已将关键响应计时与首个关闭诊断从界面状态过滤中分离：共享筛选策略同时用于无线控制器和 Activity，旧无线代次、打开菜单时也可保存，普通旧状态仍被过滤。首次关闭记录包含来源、单调时间、会话 ID、异常和 controllerGeneration。既有队列容量与日志轮转仍有效，不承诺无限保留；普通 TRACE 仍有界面状态过滤，不能把缺失 TRACE 当作请求未发生。

code45 同时将各地址族的 Bonjour close 并行执行，方法返回前等待所有关闭线程；期间持有多播锁，处理中断并恢复中断标志，线程无法启动时退回同步关闭。未改协议、重试策略、热点、图标或系统权限。外层 controller 仍保留既有有界清理等待；若日志出现 teardownWaitCompleted=false，需要继续追查，不能视为全部资源正常退出。现场仍为 code44，新包尚未安装；收益必须实车验证。实车步骤见 [code45 验收文档](VEHICLE-TEST-0.2.21-buick.1-code45.md)。

## 厂商提权与系统层调查

已确认的固件证据：

1. adbd 含厂商拒绝 root 的固定提示 `cxj said not suport, 88`，普通 adb root 受限不等于机器不存在提权能力。
2. `/system/xbin/su` 为 root 所有的 setuid 文件，含父进程 `/proc/.../cmdline` 检查、MainUI/xfapp 等名单、本机校验通信和厂商配置检查。当前 shell 调用未获得 root。
3. MainUI 的 `tool.DealSu` 通过 `ShellUtils` 启动 `su`；说明厂商软件确实使用内部提权路径。`RootSystem()` 明确包含 remount rw 和 chmod，不能在只读授权下调用。
4. xfapp 含 native 入口及 shell/命令执行路径；部分路径会落脚本、chmod、更新状态或连接远端。存在代码不等于对 ADB 开放的通用本地接口，也不能据此执行推送命令。
5. 本轮仅离线反编译、检查和一次小型只读 ADB 查询，没有通过这些入口执行命令，没有获得或宣称获得 root。

后续先追调用方校验、导出组件权限与本地 native 服务，确认存在不产生系统写入的路径后，最小验证仅运行 `id`。不修改 su、白名单、系统签名、分区挂载或 SELinux，不刷机、不关闭校验。需要系统写入的实验单列，取得用户明确授权后再做。

| 系统级方向 | 先读什么 | 可能的后续动作与边界 |
|---|---|---|
| 热点稳定与快速关联 | hostapd 真实信道、WMM、DTIM、beacon、租约、关联记录、驱动计数 | 根据信号/丢包实验选择信道与省电策略；修改配置需单独授权，不随意改 beacon/DTIM |

## 实施与验收顺序

1. 先补 C01 的响应分段与 C13 的首个关闭原因，记录连接起点，保留完整现有日志。这是给后续改造提供归因，不是以“加日志”代替提速。
2. 做 C01/C02 冷路径和 C03 配对身份核对；有实测瓶颈再选缓存/预热/减小响应策略。
3. 做 C04/C05 复用与恢复策略设计，明确哪些失败保留 AP/Bonjour/监听，哪些必须全量销毁；覆盖旧回调与用户主动退出。
4. 解决 C06–C09 长尾证据与发现/网络冲突；同步继续厂商只读提权入口调查。
5. 再按 profile 结果推进 C10–C15 亚秒优化和开机唤醒；不将系统调参当作应用缺陷的替代品。

验收分组：真正首次配对、已配对冷启动、同进程重复连接、手机离开后返回、单次异常恢复、车机冷启动、休眠唤醒。清配对实验会改变现有配对，另行安排，不直接删除当前记录。

每组至少先取 10 次作筛查，记录逐次耗时、成功率、重试次数与中位数；扩大样本后再看可靠的 P95，不能以两次成功代表长期可靠。分别统计点击/唤醒到首帧、controller 到首帧、各阶段与失败等待。正常连接时不做持续无线 ADB 导出。改善需超过对照波动，不能只挑最快一次。

研究目标为先争取稳定削减 1–2 秒并压低异常长尾，随后再定更激进目标；这不是已完成收益承诺。三分钟流畅只是当前冒烟验收，长时间稳定性、连续多次重连和冷启动仍未验收。
